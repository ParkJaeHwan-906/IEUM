# 2026-10-09 중복 요청 부하 — 비관적 락 · 낙관적 락 · Redis Lua 통합 판정

[ADR-0004](../adr/0004-reservation-path.md) 의 세 전략을 같은 날, 같은 조건으로 연달아 측정했다.
ADR-0003 의 시나리오(재고 100 / 소비자 10,000 명 × 1회) 와 달리 **같은 사용자의 요청이 서버 안에서 겹치는** 부하다.

## 시나리오

- 상품 1개, 재고 **1,000**, 소비자 **1,000 명** (사용자 수 = 재고 → 정상이면 한 사람당 정확히 1건, 201 정확히 1,000)
- 각 사용자가 같은 상품에 요청을 **4개씩 동시에**(`http.batch`) 보내기를 반복. 매 요청 새 Idempotency-Key (버튼을 여러 번 누른 상황)
- 사용자당 100 요청 → **총 100,000** (이 프로젝트의 중복 요청 기준 시나리오)
- 스크립트: `scripts/k6/duplicate-burst.js`, 토큰은 `login-tokens.js` 로 미리 발급

## 실행 조건

- Windows 11 호스트에서 `ieum-api` jar 직접 실행, MySQL 8.4 · Redis 7.4 는 Docker Desktop 컨테이너. k6 v2.2.0 도 같은 호스트
- HikariCP 20, Tomcat 스레드 200(기본), Lettuce 풀 32 (`commons-pool2` 추가로 이번부터 실제로 풀링됨 — ADR-0003 측정 때는 단일 공유 커넥션)
- `SQL_LOG_LEVEL=warn`, `SQL_BIND_LOG_LEVEL=off`, 라운드마다 `reset-loadtest.sql` + `stock:*` 키 삭제 후 API 서버 재기동
- k6 는 VU 별 첫 요청을 5ms 씩 늦춰 약 5초에 걸쳐 연결한다. 한 순간에 4,000 연결을 열면 Windows 의 listen backlog(200) 를 넘어
  40% 가 `connection refused` 였다 (`server.tomcat.accept-count` 로는 해결되지 않음). 연결 후에는 keep-alive 재사용
- 응답 분류: 201 / 409 재고 / 409 중복 / 503 / 그 외. 세 라운드 모두 "그 외" 0, `http_req_failed`(201·409 외) 는 optimistic 의 503 뿐

## 결과 — 1,000 명 × 100 요청 = 100,000

### 정합성

| | pessimistic | optimistic | redis |
|---|---|---|---|
| 201 | **1,000** | **1,000** | **1,000** |
| 409 중복 | 99,000 | 95,096 | 99,000 |
| 409 재고 | 0 | 0 | 0 |
| 503 (재시도 소진) | 0 | **3,904 (3.9%)** | 0 |
| 주문 행 / 서로 다른 사용자 | 1,000 / 1,000 | 1,000 / 1,000 | 1,000 / 1,000 |
| 사용자당 활성 예약 2건 이상 | **0** | **0** | **0** |
| 원장 잔여 | DB 0 | DB 0 | Redis 0 (활성 SET 1,000) |
| 롤백된 INSERT | 0 | 0 | 0 |
| 데드락 | 0 | 0 | 0 |

409 재고가 0 인 것은 사용자 수와 재고가 같아서다. 1,000 명이 각자 1건을 가진 뒤의 요청은 전부 "이미 진행 중인 예약" 에 먼저 걸린다.

**세 전략 모두 초과 예약 0, 사용자당 1건.** optimistic 이 중복 틈을 닫은 이유는 ADR-0004 2절 (같은 행의 `version` 이 스냅샷 이후의 커밋을 드러냄).

### 비용

| | pessimistic | optimistic | redis |
|---|---|---|---|
| 소요 시간 | 5분 14초 | 1분 33초 | **27초** |
| 처리량 | 319 req/s | 1,082 req/s | **3,672 req/s** |
| k6 지연 중앙값 / p95 / p99 | 11.95s / 14.4s / 19.1s | 2.55s / 9.81s / 15.3s | **0.86s / 1.88s / 2.22s** |
| 서버 측 평균 — 409 | 621ms | 150ms | **50ms** |
| 서버 측 평균 — 201 | 1,145ms | 552ms | 421ms |
| HikariCP 커넥션 획득 | 100,002 | 111,836 | **1,011** |
| 커넥션 획득 대기 평균 | 562ms | 146ms | 224ms |
| InnoDB 행 락 대기 (증가분) | **99,999** · 합 5,777s | 16,635 · 합 368s | **0** |
| `@Version` 충돌 / 소진 | 0 / 0 | 15,738 / 3,904 | — |
| Redis `evalsha` 서버 측 | — | — | 12.6µs / 호출 |

k6 지연은 요청이 Tomcat 큐(동시 4,000 / 스레드 200) 에 선 시간까지 포함한다. 그래서 서버 측 평균보다 훨씬 크다. 전략 간 비교는 서버 측 평균과 처리량으로 본다.

### 읽은 것

1. **비관적 락: 정합성은 가장 단순하게 맞지만, 거절도 줄을 선다.** 행 락 대기 99,999 = 요청 수 − 1 이다. 첫 요청 하나만 빼고 **모든 요청이 상품 행 잠금을 기다렸다**.
   99,000 건이 "이미 예약 있음" 으로 거절될 요청인데도 거절하려면 잠금을 받아야 한다. 409 의 서버 측 평균이 621ms 로 201 보다 조금 짧을 뿐인 것이 그 증거다.
   처리량 319 req/s 는 "한 행 잠금 보유 시간(≈ 3ms) 의 역수" 에 해당하며 커넥션을 늘려도 오르지 않는다 (같은 행에 줄을 서므로)
2. **낙관적 락: 잠금 대기는 1/6 이지만 3.9% 에게 답을 못 준다.** 거절 대부분은 잠금 없이 읽고 409 로 끝나 처리량이 3.4배다.
   대신 재고가 있는 동안 같은 행에 몰린 요청이 `version` 충돌을 반복해 15,738 회 충돌, 3,904 건이 상한(3회) 을 넘겨 503 이 되었다.
   이 503 은 "재고도 있고 중복도 아닌데 거절된" 요청이 아니라 대부분 중복 요청이 재시도 중에 소진된 것이다 (사용자 1,000 명 모두 결국 1건씩 가졌다).
   그래도 클라이언트가 받는 것은 409 가 아니라 503 이라 의미가 흐려진다
3. **redis: 거절이 DB 에 닿지 않는다.** 커넥션 획득 1,011 회 = 성공 1,000 + 워밍업·조회 소수. 99,000 건의 거절은 Lua 한 번(서버 측 12.6µs) 으로 끝났고 행 락 대기 0.
   409 서버 측 평균 50ms 중 대부분은 Redis 가 아니라 **Lettuce 풀(32) 을 Tomcat 스레드 200 이 나눠 쓰는 대기** 다 (`stock.redis.script` 애플리케이션 측 평균 47ms).
   다음 튜닝 지점은 Lettuce 풀 크기 또는 파이프라이닝이며, DB 쪽이 아니다

## 1,000,000 요청을 기준으로 삼지 않은 이유

사용자당 1,000 요청(총 1,000,000) 도 시도했으나 첫 전략 측정 중 호스트 메모리가 부족해 중단되었다 (k6 1,000 VU ≈ 1GB, ieum-api ≈ 1GB, MySQL·Redis 컨테이너가 같은 PC).
100,000 에서 이미 세 전략의 정합성과 비용 차이가 분명해 기준 시나리오를 100,000 으로 정했다 (2026-10-09). 중단된 원자료 `burst-redis-20261009-201845` 는 쓰지 않는다.
