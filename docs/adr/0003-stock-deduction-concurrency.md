# ADR-0003. 한정 재고 차감의 동시성 제어 — 세 방식을 같은 부하로 비교한다

- 상태: **결정** (2026-09-23. 1단계 → 2단계 라운드 1·2 → 조건부 UPDATE → 3단계 두 라운드 → synchronized 두 라운드까지 같은 시나리오로 측정)
- 날짜: 2026-09-12 (방식 결정·1단계 측정), 2026-09-14 (1단계 재측정·2단계 라운드 1), 2026-09-16 (1단계 계측 포함 재측정), 2026-09-17 (2단계 라운드 2, (선택) 조건부 UPDATE), 2026-09-23 (3단계 두 라운드, synchronized 두 라운드, 결정)
- 관계: README 의 "부하가 증가해도 데이터 정합성을 깨뜨리지 않는 시스템" 목표를 예약 생성 경로에서 구체화한다.
  측정 기록은 [docs/performance](../performance/) 에 라운드별로 남긴다

## 배경

예약 생성은 `StoresItems.remainingQuantity` 하나를 두고 다수의 소비자가 동시에 경쟁하는 경로다.
불변식은 `initialQuantity = remainingQuantity + 활성 예약 수량 + 픽업 완료 수량` 이며, 이것이 깨지면
재고보다 많은 예약이 받아들여진다(초과 예약).

이 프로젝트는 "어떤 방식이 맞는가" 를 결론만 적는 대신, **같은 시나리오(재고 100 / 요청 10,000)로
세 방식을 모두 측정해 차이를 숫자로 남기는 것** 을 목표로 한다. 그래서 세 구현체를 모두 두고
`STOCK_STRATEGY` 로 갈아 끼운다.

## 검토한 방식

세 방식 모두 `StockDeductionStrategy` 인터페이스의 구현체이며 `ieum-api` / `orders/stock/` 에 있다.

### 1단계. 잠금 없음 (`naive`) — 실패를 보이기 위한 기준선

`remainingQuantity` 를 조회하고, 애플리케이션에서 뺀 값을 `UPDATE` 로 덮어쓴다.

동시에 같은 값을 읽은 트랜잭션들이 각자 "읽은 값 − 1" 을 쓰므로 앞선 차감이 사라진다(lost update).
MySQL 의 기본 격리 수준(REPEATABLE READ)에서 읽은 값은 모두 커밋된 값이므로 dirty read 는 아니다.
`UPDATE` 가 행 잠금을 잡아도 잠금 전에 계산된 값이 기록되므로 막지 못한다.

### 2단계. `@Version` 낙관적 락 (`optimistic`)

`StoresItems.version` 을 두고 `UPDATE ... WHERE id = ? AND version = ?` 로 쓴다. 읽은 뒤 누군가 먼저
썼다면 `OptimisticLockException` 이 나고, 트랜잭션 바깥에서 새 트랜잭션으로 재시도한다.

정합성은 맞는다. 측정하려는 것은 그 비용이다. 요청 10,000 이 재고 100 을 두고 경쟁하면 대부분이
충돌·재시도를 겪으며, 재시도 폭주가 DB 커넥션 대기와 p99 를 얼마나 밀어 올리는지 본다.

### (선택) 조건부 UPDATE 한 문장

`UPDATE stores_items SET remaining = remaining - ? WHERE id = ? AND remaining >= ?`.
`@Version` 없이도 정합성이 맞고 재시도가 없다. 2단계와 3단계 사이의 데이터 포인트로, 낙관적 락의
비용이 "충돌 검출" 에서 오는지 "재시도" 에서 오는지 분리해 보여 준다. 시간이 허락하면 측정한다.

### 3단계. Redis Lua Script (`redis`)

Redis 를 재고 원장으로 두고 Lua 스크립트 안에서 조회·검사·차감을 한 번에 실행한다. Redis 는 단일
스레드로 스크립트를 원자적으로 실행하므로 읽기와 쓰기 사이의 틈이 없다. DB 는 결과를 기록한다.

문제가 "동시성" 에서 "Redis ↔ DB 정합성" 으로 옮겨 간다. 재고 복구 멱등성(예약당 1회), Expiry Worker,
Reconciliation 이 그 답이며 todo 2.2 에 있다.

### (비교용) `synchronized` — JVM 모니터

"가장 먼저 떠오르는 방법" 이라 같은 시나리오로 두 범위를 측정했다 (`STOCK_STRATEGY=synchronized`, `STOCK_SYNC_SCOPE`).
트랜잭션 **안**(차감 메서드만) 에 걸면 모니터가 풀린 뒤 커밋되므로 다음 요청이 커밋 전 값을 읽어 초과 예약이 난다.
트랜잭션 **밖**(예약 생성 호출 전체) 에 걸면 정합성은 맞지만 재고 부족 409 까지 전부 한 줄로 직렬화된다.
어느 범위든 프로세스 하나 안에서만 유효해 다중 인스턴스(V3) 에서는 무의미하다.

### 채택하지 않은 것 — 분산락 (SETNX / Redisson)

락 TTL 과 커밋 전 해제 문제가 있고, 여전히 직렬화라 처리량 상한이 락 보유 시간에 묶인다.
Lua 스크립트가 같은 원자성을 더 짧은 임계 구역으로 제공하므로 절충안으로만 기록한다.

## 결정

**예약 생성 경로의 재고 차감은 3단계 Redis Lua (`redis`) 로 간다.** 한 상품에 몰리는 경합에서 정합성을 지키면서 재고 행 직렬화를 없애는 것은
측정한 여섯 방식 중 이것뿐이었다 (행 락 대기 0, 재고 소진 0.40~0.69초, 보상 0). 처리량·p99 는 conditional 과 같은 자릿수이며 라운드 간 편차 안이고,
그 원인(Lua 호출이 DB 커넥션 보유 중에 실행됨, Lettuce 단일 공유 커넥션) 은 아래 "Redis ↔ DB 정합성과 다음 실험" 에 적었다.

`conditional` 은 두 번째 답으로 남긴다. Redis 를 재고 원장으로 운영할 부담(Reconciliation, 투영 갱신, 단일 장애점) 을 지기 어려운 환경이거나,
한 상품의 성공 처리 상한 ≈ 130 건/s 로 충분한 트래픽이면 `@Version` 없이 SQL 한 문장으로 같은 정합성을 얻는다.
`optimistic` 은 재고 한 행만 지키는 경로에서 `conditional` 보다 나은 점이 없었고, `synchronized` 는 범위를 맞춰도 처리량이 1/3 이며 인스턴스 하나를 넘지 못한다.

측정에서 확인된 것은 다음과 같다.

- 잠금 없는 차감은 100 VU 동시 요청에서 재고의 약 20배를 통과시킨다. 기준선으로서 역할을 다했다
- `@Version` 은 초과 예약을 없앤다. 201 이 정확히 100, `version` 이 정확히 100, 불변식 성립 (2단계 라운드 1)
- 그러나 `@Version` 만으로는 부족했다. 19% (1,926건) 가 MySQL 데드락으로 500 을 받았다. 원인은 `@Version` 이 아니라 SQL 순서다.
  IDENTITY 로 즉시 나가는 `INSERT users_orders` 가 FK 검사로 `stores_items` 에 S 락을 잡고, flush 때 나가는 `UPDATE stores_items` 가
  같은 행에 X 락을 요구해 두 트랜잭션이 서로의 S 락에 막힌다. naive 가 데드락이 없었던 것은 벌크 UPDATE 가 INSERT 보다 먼저 실행되기 때문이다.
  "재고 행 밖의 불변식" 이 문제가 아니라 **재고 행을 누가 어떤 순서로 잠그느냐** 가 문제였다
- 라운드 2 에서 `decreaseQuantity` 직후 flush 해 UPDATE 를 INSERT 앞에 보냈다. 500 0, `deadlock` 카운터 0, InnoDB 데드락 기록 없음.
  version 검사가 INSERT 앞으로 오면서 실패 시도의 INSERT 낭비도 0 이 됐다 (라운드 1 ≈ 2,048). 그 대가로 데드락이 미리 죽여 주던 경쟁자들이
  version 검사까지 오게 되어 충돌 137 → 1,894, 503 은 4 → **574 (5.7%)**. 이것이 상한 3 에서 "재고가 있는데 답을 못 준 요청" 의 진짜 값이다.
  flush 이후 커밋까지 X 락을 쥐므로 이 구현은 순수 낙관적 락이 아니라 "짧은 비관적 락 + version 검증" 에 가깝고, 재고 한 줄의 UPDATE 가
  직렬화되어 p99 가 716 → 790ms 로 올랐다 (중앙값은 소진 후 409 비중이 커져 114 → 93ms)
- 지연의 정체는 HikariCP 대기다. `pending` 이 예약 구간 내내 72~80 (VU 100 − 풀 20), `acquire` 평균 119ms ≈ 예약 중앙값 114ms.
  DB 가 아니라 풀 앞의 줄이 요청 시간을 만든다. naive 도 같은 계측에서 `pending` 80, `acquire` 평균 141ms 였으므로(09-16) 이 줄은
  전략의 비용이 아니라 실험 조건의 성질이다. 전략 간 비교는 이 줄 위에서 무엇이 달라지는가(롤백된 INSERT naive 0 대 optimistic ≈ 2,048, 데드락, 재시도) 로 본다.
  3단계에서 Redis 가 DB 왕복을 줄이면 이 줄이 얼마나 짧아지는지가 비교 포인트
- 재시도 계층은 설계대로다. 라운드 2 기준 충돌 1,894 회 중 64 회는 성공으로 이어졌고(2회 18건, 3회 23건), 108 회는 재시도에서 재고 0 을 읽고 409,
  1,722 회(574건 × 3)는 소진. 백오프 `[0, 10ms × 시도]` 균등 난수(full jitter)는 X 락 보유 시간보다 짧아 같은 대기 줄에 다시 서는 경우가 많았을 것이다.
  상한을 올리면 503 은 줄고 p99·`pending` 은 오른다. 그 트레이드오프는 3단계가 직렬화를 DB 밖으로 옮긴 결과를 본 뒤 필요하면 잰다
- **낙관적 락 비용의 분해 (조건부 UPDATE, 09-17).** `@Version` 도 재시도도 없이 `UPDATE ... WHERE remaining >= ?` 한 문장으로 바꾸자
  201 정확히 100, 불변식 성립, `version` 0 인 채로 **503 0, 충돌 0, 커넥션 획득 정확히 10,000**. 라운드 2 의 503 574 는 재고 경합의 값이 아니라
  "락을 받은 뒤 version 을 비교하고 상한 3 에서 포기하는" 재시도의 산물이었다. 같은 행의 X 락에 줄을 서는 것은 둘 다 같고, 락을 받은 뒤
  version 을 보느냐 재고를 보느냐만 다르다. 재고 100 이 0.76초에 소진됐고 (라운드 2 는 5초), 처음 잰 행 락 대기는 118회 · 평균 117ms · 최대 227ms 로
  풀 20 이 한 행에 줄을 선 길이(≈ 19 × 보유 7.6ms) 와 맞는다. 라운드 2 의 백오프 10~30ms 는 이 줄 대기보다 한 자릿수 짧았다.
  p95 491 → 236ms, p99 790 → 669ms 로 내려갔지만 p99 는 재시도가 전혀 없는 naive 의 633ms 와 같은 수준이라, **이 부하의 p99 는 전략이 아니라
  VU 100 / 풀 20 의 커넥션 대기가 만든다.** 남는 것은 재고 한 행의 X 락 직렬화(한 상품 성공 처리 상한 ≈ 130 건/s), 규칙이 SQL 로 내려간 것,
  중복 활성 예약 검사의 틈이며, 이 셋이 3단계에서 Redis 로 옮길 목록이다. 재고 한 행만 지키면 되는 경로에서는 `@Version` 이 추가로 주는 것이 없었다
- **3단계 Redis Lua (09-23, 두 라운드).** 원장을 `stock:{itemId}` 로 옮기고 예약 트랜잭션에서 `stores_items` UPDATE 를 없앴다. 201 정확히 100, 보상 0, 워밍업 0,
  **`Innodb_row_lock_waits` 증가분 0** (conditional 118), 재고 소진 0.40 / 0.69초 (conditional 0.76, synchronized 1.70). DB `remaining_quantity` 는 100 그대로, `version` 0 —
  원장이 DB 밖으로 나갔다는 직접 증거. Redis 쪽 `evalsha` 는 호출당 20µs 로 병목이 아니다. 그러나 p99 808 / 589ms, 처리량 633 / 455 req/s 로 conditional(669ms / 758) 보다
  좋지 않았다. 정합성 지표가 완전히 같은 두 라운드가 지연에서 이만큼 갈려, 이 환경에서 ±100ms 의 p99 차이는 전략의 차이가 아니다. 구조적 원인은 하나 있다.
  Lua 호출이 `create` 트랜잭션 안(커넥션 보유 중) 에서 실행되고, 애플리케이션이 잰 스크립트 시간이 평균 4.3~5.8ms (서버 20µs) 라 소진 후 9,900 건의 커넥션 보유가
  그만큼 늘어난다. `commons-pool2` 가 없어 Lettuce 가 네이티브 커넥션 하나를 100 스레드가 공유하는 것이 그 5ms 의 정체다
- **`synchronized` 두 라운드 (09-23).** 트랜잭션 밖에 걸면 201 정확히 100, 행 락 대기 0, `active` 최대 1 / `pending` 0 — 줄이 DB 풀 앞에서 JVM 모니터 앞으로 옮겨 갔을 뿐이고
  풀 19 개가 논다. 처리량 204 req/s, p99 1.41s, 중앙값 463ms. 트랜잭션 안에 걸면 201 이 2,854 로 naive(1,996) 보다 더 뚫렸다. 모니터가 UPDATE 순서만 정하고
  읽는 값(영속성 컨텍스트 캐시·REPEATABLE READ 스냅샷) 은 못 바꾸기 때문이며, 행 락 대기 2,853 = 성공 − 1 이 "모니터 해제 후 커밋" 을 InnoDB 가 세어 준 값이다

## Redis ↔ DB 정합성과 다음 실험

3단계에서 문제는 "동시성" 에서 "Redis ↔ DB 정합성" 으로 옮겨 갔다. Redis 차감과 DB INSERT 는 한 트랜잭션이 아니므로 시점을 셋으로 나눴다
(차감은 즉시, 보상 `INCRBY` 는 `afterCompletion(STATUS_ROLLED_BACK)`, 복구·초기화는 `afterCommit`). 남는 창은 둘이다.

1. Lua 차감 후 커밋 전에 프로세스가 죽으면 보상이 안 돌아 재고가 샌다
2. 취소 커밋 후 `afterCommit` 전에 죽으면 복구가 안 된다 (`afterCommit` 의 예외는 전파되어 클라이언트는 500, DB 는 CANCELED)

둘 다 DB 주문 상태로 Redis 값을 다시 계산하면 잡힌다. 재고의 진실은 Redis 값이 아니라 **DB 의 주문 상태** 이고, `initial − 활성 주문 수량` 이 Redis 가 가져야 할 값이다.
그것을 주기적으로 대조해 고치는 Reconciliation Job 은 "선택" 이 아니라 **필수** 다. 워밍업(`SET NX`) 이 DB 투영 `remaining_quantity` 에서 값을 가져오므로,
투영이 stale 이면 Redis 재기동 후 원장도 stale 이 되기 때문이다. 복구 상한(`initial`) 검사도 Redis 에 없어 같은 Job 이 불변식으로 잡는다.

측정 순서로 둔 다음 실험:

1. 사전 검사(판매 조건·중복 활성 예약) 와 Lua 판정을 DB 트랜잭션 앞으로 → 소진 후 요청이 커넥션 없이 409. README V1 의 "하나의 원자적 연산" 방향
2. `commons-pool2` 로 Lettuce 풀링 → 애플리케이션 측 스크립트 시간 5ms 가 얼마나 내려가는지
3. Reconciliation Job + DB 투영 갱신 + 조회 API 가 Redis 를 보게
