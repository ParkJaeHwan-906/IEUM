# ADR-0002. 토큰 발급은 별도 프로세스로, 검증은 각 인스턴스에

- 상태: 승인됨
- 날짜: 2026-09-07 (결정), 2026-09-12 (기록)
- 관계: [ADR-0001](./0001-authentication.md) 의 결정 중 **"프로세스는 나누지 않는다"** 를 대체한다.
  서명 토큰, default-deny, 두 층 인가, 토큰에서 사용자 식별자 추출은 그대로 유효하다.

## 배경

ADR-0001 은 인증 발급(`auth.issue`)과 검증(`auth.verify`)을 패키지로만 나누고 하나의 프로세스에
두기로 했다. "나중에 분리해야 할 때 `issue/` 만 옮기면 된다"는 경로를 열어 두는 것이 목적이었다.

그 직후 V3 Kubernetes 배포 그림을 구체화하면서 조건이 하나 추가되었다.

**API Pod 이미지에는 개인키를 다루는 코드가 없어야 한다.** 수평 확장되는 API Pod 는 개수가 많고
외부 트래픽을 직접 받는다. 그 이미지 안에 비밀번호 검증, 개인키 로딩, 토큰 서명 코드가 들어 있으면
Pod 하나가 뚫렸을 때 공격자가 얻는 것이 "토큰 검증 우회"에서 "임의 사용자 토큰 위조"로 커진다.
개인키가 환경변수로 주입되지 않아 실제로는 서명할 수 없다 해도, 코드가 있다는 사실 자체가
공격 표면이고 이미지 검사 대상이다.

패키지 분리로는 이 조건을 만족할 수 없다. 하나의 JAR 은 하나의 이미지다.

## 검토한 대안

### A. Gradle 멀티모듈 — 채택

저장소 하나 안에서 `ieum-domain`(엔티티·리포지토리), `ieum-auth`(발급), `ieum-api`(검증·업무 API)
세 모듈로 나눈다. 각 서버 모듈이 별도 JAR 과 별도 이미지가 된다.

- 장점: API 이미지에 인증 코드가 물리적으로 없다. 엔티티는 한 모듈에서 공유하므로 스키마가 한 곳에 있다
- 단점: `src/` 재배치가 필요하고, 로컬에서 프로세스를 두 개 띄워야 한다

### B. 단일 JAR + Spring 프로파일

`--spring.profiles.active=auth` 또는 `api` 로 같은 JAR 이 역할을 바꾸는 방식.

채택하지 않았다. 구조 변경이 없다는 장점이 있지만 배경의 조건을 만족하지 못한다. API 이미지 안에
인증 코드와 개인키 로딩 코드가 그대로 들어 있고, 플래그 하나로 역할이 바뀐다. 잘못된 프로파일로
기동된 API Pod 가 곧 인증 서버가 된다.

### C. 별도 저장소

인증 서버를 독립 저장소로 분리하는 방식. 가장 확실한 분리다.

채택하지 않았다. `users`, `users_account` 엔티티를 두 저장소에서 관리해야 한다. 회원가입은 인증 서버가,
주문·리뷰의 작성자 참조는 API 서버가 같은 테이블을 쓰므로 한쪽의 스키마 변경이 다른 쪽을 조용히
깨뜨린다. 서비스가 하나뿐인 지금 단계에서 얻는 것보다 잃는 것이 많다.

## 결정

**발급은 별도 프로세스로 분리하고, 검증은 각 API 인스턴스에 남긴다.**

~~~text
ieum-domain/   엔티티·리포지토리. 두 서버가 공유
ieum-auth/     인증 서버 (8081). com.hwannee.ieum.auth.issue
               회원가입, 로그인, Refresh Token 발급·소비·폐기, JWKS 공개
ieum-api/      API 서버 (8080).  com.hwannee.ieum.auth.verify
               JWKS 로 서명 검증, role 클레임 → ROLE_* 매핑, @CurrentUser 주입, 업무 API
~~~

### 분리 범위

ADR-0001 이 기각한 두 대안이 여기서도 경계를 정한다.

- 검증까지 인증 서버에 맡기면 요청마다 네트워크 홉이 생긴다 (ADR-0001 대안 A). 검증은 공개키만
  있으면 되는 순수 암호 연산이므로 각 Pod 가 직접 한다
- 인증 서버가 헤더만 붙여 주는 방식은 클러스터 내부 위조에 취약하다 (ADR-0001 대안 B).
  API 서버는 헤더가 아니라 서명을 신뢰한다

따라서 나뉘는 것은 **발급만**이다. 발급은 로그인·재발급 시점에만 일어나고 예약 핫패스에 없으므로
분리해도 부하 테스트가 측정하려는 병목에 영향이 없다.

### 분리 때문에 필요해진 장치

- **JWKS 공개** (`GET /.well-known/jwks.json`) — 같은 프로세스였다면 공개키를 메모리에서 꺼내면 됐다.
  이제 API 서버는 인증 서버의 JWKS 를 조회해 캐시한다
- **무중단 키 교체** (`JWT_PREVIOUS_KEYS`) — 인증 서버 재시작으로 키가 바뀌면 API 서버 캐시와
  이미 발급된 토큰이 함께 무효화된다. 교체 전 키의 공개 부분을 JWKS 에 함께 실어 `ACCESS_TOKEN_TTL`
  동안 겹치게 한다
- **`kid` 헤더** — JWKS 에 키가 둘 이상 실리므로 어느 키로 서명했는지 토큰이 밝혀야 한다
- **인증 서버 default-deny** — 인증 서버는 자기가 발급한 토큰을 검증하지 않는다. `/auth/*`, JWKS,
  health 외에는 `denyAll` 이다

### 라이브러리

- 검증: `spring-boot-starter-oauth2-resource-server`. `NimbusJwtDecoder` 가 JWKS 캐싱·재조회를 내장한다
- 발급: `spring-security-oauth2-jose` 의 `NimbusJwtEncoder`. Spring Authorization Server 는 쓰지 않는다.
  Password Grant 가 표준에서 제거되어 이메일·비밀번호 로그인에 Authorization Code + PKCE 와
  로그인 페이지가 필요해지는데, 이 프로젝트의 클라이언트 구성에 맞지 않는다

## 결과

### 얻는 것

- API 이미지에 개인키 접근 경로가 없다. Pod 침해 시 피해 범위가 "검증 우회"에 한정된다
- 인증 서버 1개, API Pod N개로 독립 스케일링한다. 발급 부하와 예약 부하가 서로 영향을 주지 않는다
- 개인키 주입·키 교체·감사 로그를 인증 서버 하나에서만 다룬다
- ADR-0001 의 인증·인가 논리는 하나도 바뀌지 않았다. 검증 측 코드(`auth.verify`)는 패키지 이동만 했다

### 감수하는 것

- **로컬에 프로세스가 둘이다.** ADR-0001 은 "서버가 늘어나지 않는다"를 장점으로 꼽았고 이 결정이 그것을
  뒤집는다. `docker compose` 위에 `bootRun` 두 개를 띄워야 signup → login → API 호출을 확인할 수 있다
- **API 서버가 인증 서버 가용성에 의존한다.** JWKS 조회가 실패하면 새 토큰을 검증할 수 없다.
  `NimbusJwtDecoder` 의 캐시가 완화하지만, 인증 서버가 오래 죽어 있으면 결국 검증이 막힌다
- **`ieum-domain` 스키마 변경이 두 서버를 동시에 깨뜨릴 수 있다.** 대안 C 보다는 낫지만 하나의 모듈을
  두 서버가 공유하는 결합은 남는다. 배포 시 두 서버를 같은 커밋으로 올린다
- **Refresh Token 상태가 Redis 에 있다.** 인증 서버는 stateless 가 아니며 Redis 영속화 설정이 필요하다

### 재검토 조건

- API 서버가 둘 이상의 서비스로 나뉘어 각자 다른 인가 정책을 가져야 할 때 (ADR-0001 재검토 조건과 동일)
- 소셜 로그인 등 외부 IdP 연동이 생겨 Authorization Code 흐름이 필요해질 때 — 자체 발급기 대신
  Spring Authorization Server 또는 외부 IdP 도입을 검토한다
- 인증 서버 가용성 문제가 실제로 관측될 때 — JWKS 를 ConfigMap 등 정적 경로로 배포하는 방안을 검토한다
