# ADR-0001. 인증은 분리 가능하게, 인가는 데이터 가까이에

- 상태: 승인됨. "프로세스는 나누지 않는다" 항목은 [ADR-0002](./0002-auth-server-split.md) 에 의해 대체됨 (2026-09-07)
- 날짜: 2026-09-04

## 배경

IEUM 은 아직 서비스 계층이 없는 단계이며, 도메인 엔티티와 리포지토리만 정의되어 있다.
`spring-boot-starter-security` 의존성은 있으나 `SecurityConfig` 가 없어 모든 엔드포인트가
Spring Security 기본 설정으로 막혀 있다. 예약 API 를 만들기 전에 인증 체계를 먼저 정해야 한다.

인증을 나중으로 미룰 수 없는 이유는, 사용자 식별자가 요청 본문이 아니라 인증 정보에서 와야
하기 때문이다. 예약의 멱등 키 정책이 `userId + Idempotency-Key` 조합에 의존하므로, 사용자
식별을 신뢰할 수 없으면 멱등성 자체가 성립하지 않는다.

요구사항은 두 가지였다.

1. 인증을 거치지 않은 요청은 어떤 것도 허용하지 않는다
2. 인증 주체를 한 곳에 모은다

### 도메인 특성

- `UserType` 은 `ADMIN`, `BUSINESS_OWNER`, `CONSUMER` 세 가지다
- 기능이 점주(Merchant)와 소비자(Customer)로 명확히 갈린다
- 프로젝트의 핵심 목표는 한정 재고에 대한 동시 요청 처리 정합성이다
  (재고 100개 / 요청 10,000건 → 성공 정확히 100건)
- V3 에서 Kubernetes 다중 인스턴스로 확장할 계획이다

## 검토한 대안

### A. 인증 서버와 인가 서버를 각각 별도 서비스로 분리

요청마다 별도의 인가 서버에 허용 여부를 질의하는 구조. 표준 용어로는 PDP/PEP 모델이다.

채택하지 않았다. 세 가지 이유가 있다.

**인가 판단에 필요한 데이터가 API 서버에 있다.** 이 도메인의 인가는 대부분 소유권 검사다.
"이 `UsersOrders` 가 이 사용자 것인가", "이 `StoresItems` 가 이 점주의 `Stores` 것인가"는
모두 MySQL 을 조회해야 답할 수 있다. 인가 서버를 분리하면 DB 를 공유하거나(분리한 의미가 없고
스키마 변경이 두 서버를 동시에 깨뜨린다) 데이터를 복제해야 하는데(실시간으로 바뀌는 예약
상태를 복제본으로 판단하면 재고 정합성이 깨진다) 둘 다 받아들일 수 없다.

**핵심 목표와 충돌한다.** 모든 요청이 예약 로직에 도달하기 전에 동기 네트워크 홉을 한 번 더
거치게 된다. V1 은 Redis Lua Script 한 번으로 예약 판정을 끝내는 설계인데, 그 앞에 왕복
지연이 붙으면 측정하려던 예약 로직의 병목이 인가 서버 지연에 묻힌다. 부하 테스트 결과를
근거로 V2(Kafka) 도입을 결정하겠다는 계획 자체가 흐려진다. 인가 서버는 단일 장애점이 되어,
장애 시 조회 요청까지 전부 실패한다.

**분리가 값어치를 하는 조건이 아니다.** PDP 분리는 여러 서비스가 정책을 공유하거나, 재배포
없이 정책을 바꿔야 하거나, 감사 요구가 있을 때 이득이다. 현재는 서비스가 하나이고 역할이
셋이며 정책이 거의 바뀌지 않는다.

### B. 인증 서버가 신뢰 헤더를 주입하고 API 서버는 그것을 신뢰

인증 서버가 `X-User-Id` 같은 헤더를 붙여주고 뒷단은 검증 없이 신뢰하는 방식.

채택하지 않았다. **API 서버에 직접 요청을 보낼 수 있는 누구나 헤더를 위조해 임의의 사용자로
행세할 수 있다.** V3 에서 다중 Pod 로 확장하면 클러스터 내부에서 실제 위험이 된다.
"인증 서버를 거치지 않은 요청은 불허"라는 요구사항이 네트워크 격리에만 의존하게 되어,
격리가 뚫리는 순간 인증 체계 전체가 무너진다.

## 결정

**프로세스는 나누지 않고, 경계를 패키지에 긋는다.**

### 인증 — 서명된 토큰

인증 서버가 개인키로 서명한 JWT 를 발급하고, 각 API 인스턴스가 공개키로 검증한다.
"인증을 거쳤다"는 사실이 네트워크 구성이 아니라 암호학적으로 증명되므로, 대안 B 의 위조
문제가 원천적으로 발생하지 않는다. 검증에 외부 호출이 없어 stateless 하고 V3 수평 확장과도
맞는다.

패키지는 다음과 같이 나눈다.

~~~text
com.hwannee.ieum.auth
├── issue/      자격 증명 검증 → 토큰 발급. 로그인 시점에만 동작
└── verify/     서명 검증 → SecurityContext 주입. 각 인스턴스 내장
~~~

이 경계가 중요한 이유는, 나중에 인증 서버를 정말 분리해야 할 때 `issue/` 만 옮기면 되기
때문이다. `verify/` 는 공개키만 있으면 되므로 API 서버에 그대로 남는다. 발급은 예약
핫패스에 없으므로 분리해도 성능에 영향이 없다.

### 인가 — 두 층으로, 각자 판단 가능한 위치에

**default-deny 를 기본으로 한다.** 허용할 경로만 명시하고 나머지는 전부 차단한다.

~~~java
.authorizeHttpRequests(auth -> auth
    .requestMatchers(...).permitAll()   // 명시적 허용 목록
    .anyRequest().authenticated()        // 나머지 전부 차단
)
~~~

새 API 를 추가하고 허용 목록에 넣는 것을 잊으면, "열린 채로 방치"가 아니라 "막힌 채로 실패"
한다. 안전한 방향으로 틀리는 설계다.

그 위에 두 층을 얹는다.

| 층 | 위치 | 판단 근거 | 비용 |
|---|---|---|---|
| 역할 검사 | `@PreAuthorize` | 토큰 클레임 | DB 접근 없음 |
| 소유권 검사 | 서비스 계층 | 조회한 엔티티 | 추가 비용 없음 |

소유권 검사를 서비스 계층에 두는 것이 핵심이다. 인가 서버를 분리했다면 네트워크 왕복이
필요했을 검사가, 어차피 수행하던 엔티티 조회에 조건문 하나를 더하는 것으로 끝난다.

**"인증만 통과하면 전부 허용"은 명시적으로 배제한다.** 인증과 인가를 하나로 합치면 소비자가
상품을 등록하거나, 타인의 주문을 취소하거나, 점주가 남의 가게 재고를 조작할 수 있다.
마지막 두 가지는 재고 불변식을 직접 깨뜨리므로, 인가 없이 동시성만 보장하는 것은 의미가 없다.

### 사용자 식별자

주문 생성 시 사용자 식별자는 **반드시 토큰에서 추출한다.** 요청 본문의 `userId` 를 신뢰하면
멱등 키 정책이 무력화되고, 타인 명의의 예약이 가능해진다.

## 결과

### 얻는 것

- 인증 우회가 암호학적으로 불가능하다
- 예약 핫패스에 추가 네트워크 홉이 없어, 부하 테스트가 예약 로직의 병목을 그대로 측정한다
- 인가 판단이 데이터와 같은 트랜잭션 안에 있어 상태 불일치가 없다
- 로컬 개발 환경에 서버가 늘어나지 않는다
- 인증 서버 분리 경로가 열려 있다

### 감수하는 것

- **인가 규칙이 서비스 코드에 흩어진다.** 정책을 한눈에 보기 어려우므로, 소유권 검사를
  각자 작성하지 않도록 공통 규약을 세우고 테스트로 강제한다
- **정책 변경에 재배포가 필요하다.** 역할이 셋뿐이고 자주 바뀌지 않으므로 수용 가능하다
- **Access Token 을 만료 전에 무효화할 수 없다.** stateless JWT 의 대가다. 수명을 짧게
  가져가고 Refresh Token 을 Redis 에서 폐기하는 방식으로 대응한다

### 재검토 조건

다음 중 하나라도 성립하면 이 결정을 다시 검토한다.

- 서비스가 둘 이상으로 나뉘어 인가 정책을 공유해야 할 때
- 재배포 없이 정책을 바꿔야 하는 요구가 생길 때
- 역할이나 권한 체계가 `hasRole` + 소유권 검사로 표현하기 어려울 만큼 복잡해질 때

## 참고

- 표준 용어에서 **Authorization Server 는 토큰을 발급하는 주체**를 가리킨다(OAuth2/OIDC).
  "인증 서버 / 인가 서버"라는 두 서버 구분은 표준에 존재하지 않으며, 요청마다 허용 여부를
  질의하는 구조는 PDP(Policy Decision Point)라고 부른다. 문서와 코드에서 용어를 혼동하지 않는다.
